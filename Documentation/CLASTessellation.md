# Streamed CLAS displacement tessellation

Metallic can build ray-traceable displaced microgeometry from the published
streaming RT cut. Enable `rtTessellation` on the geometry producer:
`SceneAccelerationStructurePass`, a path-tracing pass, or a
`VisibilityBufferPass` with `enableClusterRtx=true`. The default is disabled.
The **GPU Driven / Material Displacement** sample enables both raster and CLAS
tessellation and connects the resulting TLAS to the ray-traced shadow pass.
The device must support `VK_NV_cluster_acceleration_structure`.

| Property | Default | Meaning |
| --- | --- | --- |
| `rtTessellation` | false | Enable generated CLAS geometry; changing it rebuilds the graph |
| `rtTessellationBuildMode` | `triangles` | `triangles` builds generated clusters directly; `templates` instantiates fixed topology templates |
| `rtTessellationEdgePixels` | 8 | Unjittered render-pixel edge target, 1–256 |
| `rtTessellationMaxFactor` | 4 | Leaf edge factor, 1–8 |
| `rtTessellationMaxSplitDepth` | 2 | Recursive split depth, 0–3 |
| `rtTessellationMaxPatches` | 16384 | Global generated leaf capacity; changing it reallocates the bounded arenas |

The three quality controls update the next traversal without shader variants.
The build mode changes how the same generated geometry becomes CLAS; it does
not change quality, source-domain mapping or the capacity policy. `triangles`
remains the default. Unknown build-mode values fail validation.
Raster and ray quality settings are independent; set matching values when
comparing their surfaces. Material authoring, world-unit magnitude, height
sampling, UV0 transforms and seam limitations are described in
[GPUDrivenTessellation](GPUDrivenTessellation.md).

## GPU workflow

1. Existing streaming chooses and publishes complete RT representations and
   resolves failed dynamic admissions to its terminal fallback cut.
2. One workgroup per displaced instance counts recursive leaves over that
   published cut. This includes visible instances outside the primary frustum;
   raster HZB visibility does not remove shadow/reflection contributors.
3. A bounded prefix pass admits complete instances. A second walk emits source
   page/cluster/triangle, integer patch corners and leaf edge rates.
4. One 64-thread group per leaf evaluates the shared raster split/dice pattern.
   It writes at most 64 vertex slots and 96 triangles. Actual patterns use at
   most 61 vertices. In `triangles` mode it emits an indirect triangle-build
   record; in `templates` mode it selects the template for the leaf's three
   edge rates and emits an instantiation record referencing the new vertices.
5. GPU indirect triangle builds or template instantiations write CLAS addresses
   into a contiguous arena. GPU-generated
   BLAS records group those CLAS addresses by instance. Complete BLAS results
   override their base TLAS instance addresses before the TLAS build.
6. Ray queries and ray-pipeline hits recover source barycentrics/UV/material
   identity from retained microtriangle records. Geometric normal, shading normal,
   tangent projection and ray-cone area describe the displaced microtriangle.

The implementation reuses `VisibilityTessellation` rather than duplicating its
topology generator or height sampler. Vertices are displaced in world space and
transformed back into each instance's object space, preserving world-unit
displacement under nonuniform and mirrored transforms. Each instance gets its
own generated geometry.

Generated cluster IDs start after the asset's entire fixed page/cluster ID range;
initialization checks that the generated namespace cannot wrap. Both candidate
alpha/transparent transport and committed surface decoding use the same source
domain mapping. Generated positions and triangle indices are retained because
Metallic does not use ray-tracing position fetch. Template instantiation does
not remove this per-frame dicing or index output: surface decoding still needs
the microtriangle topology, positions and source domains.

## Template initialization and steady state

The template pool contains all **512** ordered edge-rate combinations in
`[1,8]^3`, generated by Metallic's existing `makeTessellationPattern`. Each
template fixes vertex/triangle counts and triangle indices. Instantiation
supplies the current displaced vertices and the generated cluster-ID offset;
the template's cluster and geometry ID bases are zero.

Production template records use a **zero bounding-limit address**, meaning no
bounding-box constraint. This is not a zero-sized bounding box. Source
transforms and world-unit displacement may place generated vertices outside
the canonical barycentric triangle used to initialize the template, so a
guessed canonical bound would be incorrect.

The first template use allocates the pool and records its native build before
instantiation. Initialization becomes accepted only with submission; cancelled
recording must retry it. The pool and its address table remain alive through
all consumers and are shared across capacity or build-mode replacements.
Subsequent frames reuse the initialized topology but still perform selection,
count/emit, vertex dicing, CLAS instantiation, BLAS and TLAS work.

Report first-use allocation/template construction separately from steady-state
GPU timing. The controlled A/B harness and its fixed workload, warmup,
correctness and ABBA rules are described in
[MeasureCLASTessellation](../Tools/Perf/MeasureCLASTessellation.md). No template
performance conclusion is established by this implementation description.

## Capacity, history and lifetime

An instance exceeding the remaining patch capacity keeps its complete base BLAS.
Missing required page attributes or a singular transform also reject the whole
instance. No partially tessellated instance is published. This fallback is
geometrically different from the displaced raster surface; increase capacity or
reduce quality when the diagnostics report rejected instances.

The resource inspector exposes `tessellationCounts` (patches, built instances,
capacity rejections, invalid-input rejections), `tessellationLeaves`, and
`tessellationVertices`. The BLAS header exposes generated patch count and rejected
instance count. Allocation or unsupported native build failures propagate through
the existing renderer error path.

Generated storage reuses the runtime's dependency on all previous ray readers.
Its parameter packet is uploaded through a GPU copy into persistent device memory.
Frame retention covers the component across asynchronous consumers and capacity
or build-mode replacement. GPU semantic history compares the actual published source cut,
patches, edge rates, transforms and material revision; rebuilding identical
geometry does not reset PT/SHARC. Enable/disable and success/fallback transitions
invalidate history. Cancelled command recordings do not publish geometry or
advance history initialization.
Capacity and build-mode replacements share the prior GPU history and material generation:
success/fallback transitions invalidate once, while moving an unchanged surface
to a differently sized arena does not invalidate it. Switching between triangle
builds and template instantiation also preserves history when the published
surface is unchanged. The mode itself is not a geometric change.

## References and scope

The split/dice concepts follow Brian Karis's
[How to tessellate](https://graphicrants.blogspot.com/2026/02/how-to-tessellate.html)
and [Nanite programmable displacement](https://dev.epicgames.com/documentation/en-us/unreal-engine/nanite-virtualized-geometry-in-unreal-engine).
The CLAS workflow is informed by NVIDIA's
[vk_tessellated_clusters](https://github.com/nvpro-samples/vk_tessellated_clusters),
also available locally at `E:\vk_tessellated_clusters`. No Unreal source or
tessellation table is copied.

Both modes produce transient per-frame CLAS. The implementation does not add
mixed mini-cluster packing, persistent patch queues, or a temporal geometry
cache. The count/emit walk is bounded but
serial within each instance workgroup. Large displaced instances can therefore
be expensive even when total storage is bounded. No performance improvement is
claimed; the two build modes require same-scene measurements, with initialization
and steady state reported separately.

## Validation entry points

- `clas_indirect_triangle_build`: native indirect count/stride, canaries, range
  rejection and cancelled-command resource lifetime.
- `clas_template_patterns`: native build and instantiation of all 512 patterns;
  ray cluster/geometry IDs, distance and barycentrics, zero/nonzero bounding
  limits, indirect counts, strided records, range rejection and cancelled-command
  retention. The native test also releases source index storage before tracing
  the instantiated geometry.
- `scene_clas_tessellation`: production RenderGraph CLAS build and ray decoding,
  compared with independently evaluated microtriangles; source UV, geometry
  normal, material changes, mirrored/nonuniform transforms, offscreen queries,
  enable/disable, cancellation and capacity fallback.
- `scene_clas_tessellation_templates`: the same production lifecycle matrix in
  template mode, paired at each state with triangle mode and then restored.
  It compares hit attributes, source barycentric domains and the complete
  128x128 color/depth ray image, and checks that mode switches do not invalidate
  history. The original triangle test retains shared-edge probes; the paired
  test uses interior probes to avoid legal adjacent-triangle tie differences.
- Existing `tessellation_*`, `scene_clas_attributes*`, `stream_blas_cut_cache`,
  `stream_rt_representation_lifecycle` and `stream_clas_cut_readiness` protect
  shared geometry, decoding and publication contracts.

## Template validation and A/B (2026-10-25)

Windows x64 Release, RTX 5070 Ti, NVIDIA 621.01, existing
`build-pass-stages-nrd` configuration (NRD enabled, Streamline disabled):

- `MetallicRHITests` and `Metallic` builds passed. Shader module ownership passed
  for 378 files, and the actual bound tessellation SPIR-V passed `spirv-val`.
- All four strict synchronization cases above passed without skips or captured
  validation messages. The paired production case exercised 22 states, eight
  precise rays and a 128x128 image per state. Maximum attribute/image difference
  was zero; switching modes caused zero extra semantic-history changes.
- The A/B runner's 16 focused tests and the existing 18 MaterialBaseline tests
  passed. The final evidence verifier passed after all GPU processes completed.
- Nine existing raster tessellation, CLAS attribute, cut-cache and streamed RT
  publication tests passed. Both production A/B fixtures also passed separate
  synchronization-validation runs, including the final lightweight count
  readback. These validation-layer timings are excluded from the experiment.

The measured branch was VBuffer + ray-traced Shadows + Deferred at an explicitly
fixed internal **1444x694**, using the displaced-plane sample, identical camera,
height/material inputs, sun, exposure and quality. SIGMA, jitter, upscalers and
auto exposure were disabled on both sides. Each process used 32 warmup and 64
timed frames. Residency froze at frame 16 while tessellation and AS builds
continued. Every run produced **2048 patches, 1 generated BLAS, 0 rejections**.
HDR, depth and shadow readbacks were byte-identical across all 34 processes
(two diagnostics, 12 discovery, 20 independent confirmation).

The predeclared three discovery / five confirmation ABBA blocks completed with
no exclusions. The following milliseconds are medians of process medians from
the confirmation stage; gains and 95% intervals use its five complete block log
ratios, rather than the ratio of those two medians:

| GPU scope | Triangles ms | Templates ms | Time reduction | 95% interval |
| --- | ---: | ---: | ---: | ---: |
| CLAS operation and barriers | 0.171104 | 0.031824 | 81.42% | 81.15% to 81.69% |
| Tessellation record + publication | 3.967960 | 3.681840 | 7.03% | 5.19% to 8.84% |
| Entire measured graph | 5.527384 | 5.327304 | 3.40% | 1.27% to 5.49% |
| Ray-traced Shadows | 0.077704 | 0.082472 | -7.67% | -10.93% to -4.52% |

The shadow consumer **regressed**, even though the measured graph improved.
The protocol accepted the declared CLAS/graph targets; this is not an editor FPS,
startup, arbitrary-scene or path-tracing throughput result. Template initialization
is excluded from steady-state timing. At capacity 16384, the retained template
pool used 917535 bytes plus 1077696 auxiliary bytes. CLAS arena capacity stayed
71303168 bytes; per-frame CLAS scratch fell from 1704704 to 384 bytes. These are
allocation budgets, not whole-renderer VRAM measurements. The default remains
`triangles`; select `rtTessellationBuildMode: "templates"` to use instantiation.

Local, untracked evidence: `.tmp/clas-template-ab/experiment-01` (sealed raw
processes, identities and images), `report-02/report.md` (reviewed charts and
reproduction command), `strict-01/report.html`, and `Correctness.png`.
Earlier `diagnostic-01` through `diagnostic-03` preserve harness qualification
failures: hidden count binding, missing explicit internal resolution, and a
